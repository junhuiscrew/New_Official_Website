# Phase 3.7.3 隐私事实与最小待决策问题

- 适用范围：当前代码与 `phase37-local-https` 隔离配置
- 证据时间：2026-09-07（Asia/Shanghai）
- 文档状态：`FACT_CHECK_ONLY / NOT_APPROVED_FOR_PUBLICATION`
- 重要结论：当前只有可核对的数据处理机制，尚不足以形成可发布的中英文隐私政策；`/zh-cn/privacy/` 与 `/en/privacy/` 仍为 404。

## 1. 已核实事实

### 1.1 表单收集

公开 RFQ 表单和 API 可接收：

- 必填：公司名称、联系人、邮箱、隐私同意；
- 可选：电话、WhatsApp、国家/地区代码、公司网站、需求说明、偏好语言、营销同意；
- 来源上下文：受服务端公开路由校验的来源类型、slug、正式来源页面 URL 和内部 owner；
- 每个询价项目：项目类型、产品/型号引用或文本名称、数量、材料、螺杆直径、长度、设备品牌、设备型号、具体要求；
- 请求上下文：提交 IP 与 User-Agent；
- 可选附件：原始文件名、分类、SHA-256、上传时间、关联询价项目以及私有媒体记录。

Honeypot 只用于提交前反垃圾判断，不进入 RFQ 数据模型。公开接口拒绝额外字段，隐私同意必须为真；营销同意默认值为假。

代码证据：`apps/website/app/pages/[lang]/request-a-quote/index.vue`、`apps/website/app/utils/rfqSubmission.ts`、`apps/api/app/modules/rfq/schemas.py`、`apps/api/app/modules/rfq/models.py`。

### 1.2 当前可证实用途

- 记录和处理客户询价；
- 保存一个 RFQ 下的多个产品/定制项目；
- 依据服务端核实的公开页面记录询价来源；
- 允许销售按状态机跟进、分配和更新优先级；
- 对私有附件做类型/内容校验、恶意软件扫描状态管理和受控下载；
- 写入提交、状态变化、分配、附件上传、扫描和私有下载审计。

代码未提供“用于画像、广告投放、出售数据”等机制。该事实不等于对未来生产用途的承诺。

### 1.3 访问权限与安全边界

- RFQ 列表和详情需要 `rfq.read`；
- 状态/优先级更新和后台附件上传需要 `rfq.update` 与 CSRF；
- 分配需要 `rfq.assign` 与 CSRF；
- 私有附件下载需要 `rfq.download_private_file` 与 CSRF；
- 私有附件必须属于对应 RFQ，并且媒体状态为 `private`、桶为 `private-rfq`、扫描为 `clean`、上传为 `ready`；
- 私有下载地址有效期为 600 秒，并写入下载审计；
- 匿名附件令牌只与刚创建的公开编号绑定，当前配置有效期为 30 分钟；前端仅保存在当前页面内存，不持久化；
- 隔离实例 Admin Cookie 为 Secure、SameSite=Lax；访问和刷新 Cookie 为 HttpOnly，CSRF Cookie 可由前端读取以执行双提交校验。

### 1.4 存储、日志与备份

- 结构化 RFQ、项目、附件关联和审计记录存于 PostgreSQL；
- 附件对象存于非公开的 MinIO `private-rfq` 桶；隔离实例没有把 MinIO、PostgreSQL、Redis、API、Admin 或 Website 端口暴露到宿主机；
- Nginx 除健康检查外使用默认访问日志，可能记录请求路径和客户端地址；Docker 日志驱动、轮转和保留期未在仓库内定义；
- RFQ 记录本身保存提交 IP 与 User-Agent；`rfq.submit` 审计当前只写项目数量，未把 IP/User-Agent 复制进该审计事件；
- 项目曾为内容批次生成本地私有 PostgreSQL dump 和 MinIO 清单，但未发现可据此声明的生产自动备份计划、备份地区、加密方式或保留期。

### 1.5 保留与删除

- 当前运行配置 `RFQ_RETENTION_DAYS=730`；
- 现有任务只统计“已关闭且早于阈值”的候选数量，不自动删除 RFQ、项目、审计或私有对象；
- 仓库中没有面向客户的数据访问/更正/删除流程，也没有经批准的生产删除 SLA；
- 因此“730 天”目前只能描述为工程候选阈值，不能作为已批准的公开保留政策。

### 1.6 Cookie、遥测与第三方

- 当前受保护预览中 Analytics 和营销邮件均关闭；
- 网站遥测适配器默认 no-op；允许的事件结构不包含搜索词、表单正文或文件名；
- 未登录公开页面未发现项目自建的跟踪 Cookie；Nginx Basic Auth 本身不是站点 Cookie；
- Admin 登录使用 `junhui_access`、`junhui_refresh` 和 `junhui_csrf` 三个 Cookie；
- 当前隔离运行依赖本地 PostgreSQL、Redis 和 MinIO 容器，没有启用外部分析、广告或邮件服务；
- 生产托管商、对象存储商、邮件服务商、跨境传输和其他处理方尚未确定，不能从本地预览推断。

### 1.7 当前预览与未来生产的差异

当前实例是 staging 模式、本机 HTTPS、Basic Auth、全站 `X-Robots-Tag: noindex, nofollow`、Sitemap 关闭、Analytics 关闭、营销邮件关闭。生产域名、部署地区、日志策略、备份、邮件、监控、分析、Cookie 同意和第三方处理方均须在上线前重新核实。

## 2. 不能据现状断言的事项

以下事项没有充分事实或负责人批准，不得写入公开政策：

- 数据控制者/运营主体的法定全称、注册地址和隐私联系渠道；
- 各用途的法律依据和适用法域；
- 生产数据与备份的物理地区、跨境路径及处理方名单；
- 已批准的 RFQ、附件、日志、审计和备份保留期；
- 数据主体请求流程、身份核验方式、响应时限和删除例外；
- 是否启用 Analytics、营销邮件、CRM、客服、CDN/WAF、错误监控或云对象存储；
- Cookie 清单、保存期限和是否需要同意管理平台；
- 未成年人、敏感信息和自动化决策规则；
- 政策生效日期、版本、通知和更新机制。

## 3. 上线前最小待决策问题

1. 公开政策中的运营主体、注册地址和专用隐私联系邮箱分别是什么？
2. 网站主要面向哪些国家/地区，适用哪些隐私法律和处理依据？
3. RFQ、附件、访问日志、审计和备份各自保留多久；删除由谁批准和执行？
4. 客户如何请求访问、更正、导出或删除，身份如何核验，承诺多久答复？
5. 生产数据库、对象存储、备份、CDN/WAF、邮件、监控和 Analytics 分别由谁提供、位于何处？
6. 是否会把询价用于营销跟进；营销同意的撤回渠道与抑制名单如何管理？
7. 生产需要哪些 Cookie；是否启用非必要 Cookie，若启用应采用何种同意机制？
8. 是否接收未成年人或特殊类别数据；如不需要，表单和政策应如何明确限制？
