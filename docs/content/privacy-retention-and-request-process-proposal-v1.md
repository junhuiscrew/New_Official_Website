# 分类保留与个人信息请求人工流程提案

版本：`PRIVACY-OPS-PROPOSAL-V1`
状态：`INTERNAL PROPOSAL / NOT APPROVED / NOT IMPLEMENTED / DO NOT PUBLISH`

本提案把仍未制定的事项整理成一次可确认的最小决策集。所有期限和流程都必须由负责人另行批准；本轮没有修改配置、删除数据、读取备份或联系客户。

## 1. 分类保留决策表

| 数据类别 | 建议起算事件与判断依据 | 负责人需要确认 | 当前系统能力 / 缺口 |
|---|---|---|---|
| 未成交询盘及联系人 | 实质沟通结束、明确拒绝或不再有合理业务后续用途 | 最长保留安排、复核周期、例外及执行人 | 当前只有 `closed + 730天` 候选计数；没有自动删除 |
| 已成交相关沟通 | 履约、售后、争议和适用交易记录要求分别判断 | 保存哪些必要字段及具体期限 | 需与普通未成交询盘区分，当前未建立分类规则 |
| 客户图纸与附件 | 询价、报价、生产或售后目的结束 | MinIO、邮件副本及工作文件的处理规则 | 可定位私有附件；没有跨系统自动删除事务 |
| 访问、安全及审计日志 | 实际安全用途和适用记录要求 | 日志种类、轮转、访问人和保存规则 | 多类日志存在，尚未形成统一清单及生产配置 |
| 备份 | 恢复窗口和备份代次到期 | 位置、周期、代数、加密、权限和失效数据恢复后处理 | “本地”含义尚不明确，不能承诺即时从所有备份删除 |
| Gmail 通信 | 与询盘/履约用途对应的邮件和附件 | 人工归档/删除方式及邮件服务数据流说明 | 仅确认联系邮箱；没有网站 SMTP/API 自动流程授权 |
| 个人信息请求处理记录 | 完成请求、后续争议和必要证明范围 | 最少保存内容及期限 | 建议使用受限台账，尚未实施 |

不得直接把 `RFQ_RETENTION_DAYS=730` 作为负责人批准的期限。后续如选择期限，应先把候选查询、人工复核、例外标记、删除执行和复核证据分开设计。

## 2. 最小人工请求流程

建议状态：`PROPOSED`。

1. 通过 `junhuiscrew@gmail.com` 接收请求，由公司内部指定人员处理；公开文本不写个人姓名或虚构 DPO 身份。
2. 在受限台账登记收件日期、请求类型、公开询价编号、处理状态和经办角色；不把客户请求正文提交到公开 Git。
3. 优先核对原询盘邮箱、公开 RFQ 编号及必要业务信息。不得默认索要账号密码、完整身份证件或无关敏感材料。
4. 定位 PostgreSQL 询盘/项目记录、MinIO 私有附件、相关 Gmail 邮件和已知备份；记录“已查位置”和“尚无法确认位置”。
5. 按已批准规则判断查阅、更正、限制或删除范围及例外；需要删除时，先获得相应权限与操作授权。
6. 分系统执行并复核。不能把数据库、MinIO、Gmail 和备份描述为一次自动原子删除。
7. 向申请人说明实际完成范围、无法立即处理的位置和后续安排；保留最少必要的处理凭据。

本稿不承诺 24 小时、15 天、30 天或其他固定答复期限。适用期限、身份核验强度和例外处理应在生产地域、目标市场及实际流程明确后统一确认。

## 3. 首发不推广邮件的执行边界

- 首发业务决定是“不另行发送推广邮件”，本地营销邮件开关保持关闭。
- 当前 RFQ UI/API 仍存在可选 `consent_marketing` 字段，所以不能写“系统中不存在营销同意字段”。
- 如负责人决定首发移除无用途的营销选择，应另行授权 UI/API 变更并回归验证；本轮未改动。
- 隐私同意和营销同意不得合并成一个强制选项。
